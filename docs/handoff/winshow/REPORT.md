# Zephyr 窗口不出现、进程越点越多：排查报告

结论：在 Windows 上已经稳定复现出和反馈一模一样的现象。触发条件是主窗口已经被销毁（「轻量模式」下关窗）时再点图标：主实例在单实例回调里同步重建窗口，主线程从此永久卡住，新窗口一直不显示，之后每点一次图标就多一个卡住的 Zephyr 进程。触发条件和现象都已实测确认。卡住的具体原因是「在单实例消息处理函数里同步建 WebView2 窗口」，这一点有强证据，但验证用的对照实验没跑完，所以还没有改代码，也没有开 PR。

调查时间：2026 年 11 月 19 日至 25 日。代码基于 main 5f90f3f（#2517）。复现用的是 v2.5.0 便携版，这条路径上的代码 v2.5.0 和 main 一致。

## 症状

用户反馈：Zephyr 有时「不在」，狂点图标也不出来，任务管理器里却有一大堆 Zephyr 进程。用户这边没能复现，也没有日志。从「任务管理器」这个说法看，反馈来自 Windows。

## 复现结果（已确认）

在 GitHub Actions 的 windows-latest 上跑了 v2.5.0 便携版，用 PowerShell 和 Win32 API 枚举窗口，检查可见性、是否挂起，并用 3 秒超时的 SendMessageTimeout 探测主线程有没有响应。运行编号 44563457902。

| 场景 | 设置 | 操作 | 结果 |
|---|---|---|---|
| S1 | 默认 | 窗口可见时再启动一次 | 第二个进程 1 秒内退出，正常 |
| S2 | 关闭到托盘，非轻量模式 | 关窗（窗口只隐藏），再启动 | 第二个进程退出，窗口重新显示，正常 |
| S3 | 关闭到托盘 + 轻量模式 | 关窗（窗口被销毁），再启动 | 复现 |

S3 的详细过程（时间是运行日志里的时间）：

- 16:15:06 关窗后主窗口不存在，主实例（pid 7884）正常响应。
- 16:15:12 第二次启动（pid 2644），20 秒后仍未退出。
- 16:15:35 主实例变成 Responding=False。新建了一个 "Tauri Window"，但 visible=False、hung=True。单实例消息窗口和主窗口对 3 秒超时探测都不回复。
- 之后又启动 3 次（pid 7136、6992、7100），每次都不退出，进程一个个堆起来。卡住的进程很快也变成 Responding=False。
- 主实例直到任务超时被取消都没有恢复，挂了大约 30 分钟以上。探测脚本后来对这个挂起窗口调了 ShowWindow，也一起被卡住。

这和反馈的「窗口不出来、点图标没用、任务管理器里一堆 Zephyr」完全一致。

## 根因分析

### 调用链（代码位置）

1. `apps/desktop/src-tauri/src/lib.rs` 约 1779 行：单实例插件的回调直接调用 `show_or_recreate_main_window(app)`。
2. `tauri-plugin-single-instance` 2.4.2 `src/platform_impl/windows.rs`：Windows 上第二个进程用 `SendMessageW(WM_COPYDATA)` 把参数发给主实例的隐藏窗口，**没有超时**。主实例在这个窗口的窗口过程里，也就是在**处理跨进程 SendMessage 的过程中**，同步执行上面的回调。第二个进程会一直等到回调返回。
3. `lib.rs` 中的 `show_or_recreate_main_window`（约 680 至 765 行）：窗口存在且被判为存活时，走快速路径只调 `show()`，S1、S2 证明这条路没问题。窗口不存在或被判为已死时，走慢速路径：`destroy()` 之后调 `recreate_main_window(app)` 同步重建。
4. `tauri-runtime-wry` 2.12.2 `src/lib.rs` 约 263 行的 `send_user_message`：在主线程上调用时直接内联执行，不会排进事件循环。所以建窗口就发生在 WM_COPYDATA 的处理函数里。
5. `wry` 0.57.0 `src/webview2/mod.rs` 约 350 至 420 行：创建 WebView2 环境和控制器时，用 `webview2_com::wait_with_pump` 一边转嵌套消息循环一边等异步完成。

复现结果是：主线程在第 5 步之后不再处理任何消息，新窗口已经创建但一直没显示。第二个进程卡在第 2 步的 SendMessageW 上，之后每个新进程也都一样。

### 有多确定

- **触发条件（主窗口不存在时点图标）和现象：确定**，Windows 上实测复现。
- **卡死发生在「单实例回调里同步重建窗口」这条路径上：很确定。** S1、S2 走的是同一个回调，只是没进重建分支，都正常；进了重建分支就卡。Tauri 2.12.4 自己的文档（`src/webview/webview_window.rs`，WebviewWindowBuilder::new 的 Known issues）也写明，在 Windows 上从同步的处理函数里建窗口会死锁，应该改为在别的线程里建，并引用了 wry#583。
- **具体死锁机制：未确认。** 也就是 WebView2 初始化到底等在哪个调用上，以及「在跨进程 SendMessage 的处理函数里」是不是必要条件，还是在任何地方销毁后马上同名重建都会卡。为此准备了第二个对照实验：自己编译 main，加一个环境变量开关，把重建挪出回调（从新线程用 `run_on_main_thread` 投递回事件循环），和原路径对比，同时用 cdb 抓主线程调用栈。实验因收尾被取消，构建还没跑完，**没有结果**。如果改成延后执行后仍然卡，根因就是「销毁后立即重建」本身，修法会不一样。

### 哪些用户会碰到

根据 `is_webview_alive`（`lib.rs` 627 至 657 行），会进入重建分支的情况有：

- **开了轻量模式**（`lightweight_mode`，默认关闭，`lib.rs` 约 2025 行的关窗处理会直接销毁窗口），关窗后再点图标：**已复现。**
- **WebView2 渲染进程崩溃**，心跳被置成 `i64::MIN`，之后再点图标：按代码会走同一路径，**未实测。**
- **窗口可见但心跳超过 45 秒**（`HEARTBEAT_TIMEOUT_SECS` = 15 × 3）。窗口隐藏时会直接判为存活，但最小化的窗口 `is_visible()` 仍是 true。如果 WebView2 在最小化时节流了前端 15 秒一次的心跳定时器，默认设置的用户「最小化一段时间后再点图标」也可能触发。这一条**纯属推测，未验证**。第一次探测本来安排了「最小化 7 分钟后再启动」的场景，但被前一个场景卡住，没跑到。

## 排除或基本排除的方向

- **第二个进程绕过单实例、启动成完整实例：** 插件先于所有窗口初始化（Tauri `app.rs` 的 build 流程），复现里堆起来的进程也都卡在 SendMessageW、没有窗口，排除。
- **退出时清理卡住导致残留：** Tauri 的 `on_event_loop_event` 先调插件的 `on_event`，插件会在 `RunEvent::Exit` 时释放互斥量、销毁消息窗口，然后才执行 Zephyr 自己的 Exit 处理。所以就算退出清理卡住，新进程也会正常启动成新实例，不会堆积。不能解释这个症状。
- **托盘菜单重建时的锁顺序死锁：** `tray.rs` 的代码明确没有在持锁时调用 set_icon 或 set_menu（约 143 行的注释和 994 至 1340 行的实现）。在查过的范围里没发现持锁跨主线程调用的情况。
- **提权重启路径：** `elevation.rs` 对已提权实例用的是 `SendMessageTimeout`，带超时，不会无限卡住。前任实例没退出时有专门处理。没发现会造成堆积的问题。
- **窗口位置恢复到屏幕外：** `tauri-plugin-window-state` 恢复位置时会检查是否和显示器相交。复现里窗口是 visible=False，不是跑到屏幕外。不是这次的原因。
- **内核进程被当成 Zephyr：** 内核叫 `zephyr-mihomo.exe`，复现里堆起来的是 `Zephyr.exe` 本身。
- **issue #217：** 截图 OCR 出来是「创建内核目录失败」的错误弹窗，和本症状无关。
- **Linux 和 macOS：** Linux 上插件走 D-Bus，回调在 zbus 线程上执行，第二个进程最多等 D-Bus 的 25 秒超时就退出，不会无限堆积。macOS 从 Dock 打开时系统通常只激活已有实例。这两个平台都只看了代码，没有实测。

## 还没查完的

- 128 个同步命令在主线程上执行，没有逐个审查它们会不会长时间阻塞。例如 Linux 和 macOS 上网络优化会同步等 pkexec 或 osascript 的授权框。这类阻塞会让窗口卡住，但窗口本身仍然可见，和这次的症状不同。
- 前端在 `initApp` 完成后才调 `show_main_window`（`apps/desktop/src/main.js` 约 440 至 600 行）。如果前端在那之前就失败，窗口会一直隐藏，但再点图标会走快速路径把窗口显示出来，不会堆进程，所以不是这次的主因。

## 建议的下一步

1. **把对照实验跑完**（脚本是现成的，重新推一次探测分支就能跑，大约 40 分钟）。看两件事：重建挪到回调外以后是否不再卡；cdb 抓到的主线程调用栈卡在哪里。
